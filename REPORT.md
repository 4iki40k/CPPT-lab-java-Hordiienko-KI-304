Замінити список прийнятих записів параметризованим сховищем, додати власний

## 4. Контракт даних

Клас варіанта — UtilityReadingRecord. Поліморфну ієрархію не анотовано:
експортер обходить суперкласи, тож підтипи з власними параметрами дали б інший
набір стовпців, а чотири поля не відновили б підтип. Плоский запис створюється
з UtilityReading методом from.

| Поле | Тип | Стовпець | Інваріант |
| --- | --- | --- | --- |
| meter | String | лічильник | Непорожній, після strip |
| date | LocalDate | дата | Не null, календарна ISO-дата |
| value | double | значення | Скінченне, не від'ємне |
| tariff | double | тариф | Скінченний, не від'ємний |

Ключ round-trip — meter + date. Клас final, поля final, сеттерів немає;
equals/hashCode охоплюють усі чотири поля, числа порівнюються через Double.compare.
Порушення інваріанта в конструкторі — IllegalArgumentException; final-клас
не повертає CT_CONSTRUCTOR_THROW.

Порядок стовпців задається сортуванням Java-імен полів date, meter, tariff, value,
тому заголовок — `дата,лічильник,тариф,значення`, а не порядок переліку в умові.

## 5. Repository<T>

| Метод | Контракт |
| --- | --- |
| add(T) | Додає в кінець, null відхиляється |
| all() | List.copyOf: незмінний знімок у порядку додавання |
| find(Predicate<? super T>) | Збіги в початковому порядку, незмінний список |
| size() | Кількість записів |

Raw types і приведення не використовуються. Знімок не змінюється після
наступних add і не дає змінити внутрішній список. `? super T` дозволяє умову
для супертипу: Predicate<CostCalculable> і Predicate<Object> працюють
з Repository<UtilityReading>. Null-умова відхиляється.

## 6. @CsvColumn і DataStorageException

@CsvColumn має @Retention(RUNTIME), @Target(FIELD) і один елемент String value().
RUNTIME робить анотацію видимою для getAnnotation під час виконання; тест
з анотацією CLASS показує, що без нього рефлексія її не бачить. Анотація лише
задає текст заголовка і сама нічого не експортує.

DataStorageException — checked-виняток із конструкторами (message) та
(message, cause). Помилки файлу, CSV і рефлексії очікувані, тому компілятор
вимагає їх обробити. Першопричина не підміняється, порожніх catch немає.

## 7. Рефлексивний експортер

CsvExporter не містить назв предметних класів і розгалужень за підтипом.
Він проходить від заданого класу до Object, збирає getDeclaredFields з @CsvColumn,
сортує за іменем, а за однакових імен — за класом, і перевіряє trySetAccessible.
Клас без анотованих полів, недоступне поле або null-запис дають DataStorageException.

Заголовок і всі рядки будуються з одного набору полів. Значення — field.get
та Objects.toString з порожнім полем для null. Поле з комою, лапкою, CR чи LF
береться в лапки, лапки подвоюються. Записи завершуються System.lineSeparator().
write створює батьківські каталоги та пише UTF-8 з CREATE, TRUNCATE_EXISTING, WRITE,
тому коротший експорт не залишає старих рядків. IOException і IllegalAccessException
обгортаються з причиною. Порожній список дає файл лише із заголовком, тому
Class<T> передається окремо.

Універсальність перевірено на тестовому класі Book іншої предметної області
(String, int, enum і поле без анотації), на ієрархії Base/Derived та класі без анотацій.

## 8. CSV-парсер і round-trip

Файл читається повністю через Files.readString з UTF-8, бо поле в лапках може
містити перенесення. CsvParser.parseDocument — машина станів «поза лапками»,
«у лапках», «лапки закриті». Кома та перенесення в лапках — дані, `""` — одна лапка.
CRLF, LF і CR поза лапками завершують запис; завершальне перенесення не дає
порожнього запису. Незакриті лапки, символ після закритих лапок або лапка
в полі без лапок — DataStorageException з номером запису.

readCsv порівнює перший запис з CsvExporter.header і відновлює кожний наступний
через fromFields: кількість полів, LocalDate.parse, Double.parseDouble, конструктор.
Файл лише із заголовком — порожній список, повністю порожній файл — помилка.

Фактичний out/readings.csv для data/storage.csv:

```text
дата,лічильник,тариф,значення
2026-09-01,Електроенергія,4.32,120.5
2026-09-01,"Вода, гаряча",98.5,3.2
2026-09-01,"Вода, холодна",35.94,6.8
2026-09-01,"Газ ""Схід""",7.96,25.0
2026-10-01,Електроенергія,4.32,133.25
2026-10-01,"Вода, гаряча",98.5,0.0
```

--export кладе записи в Repository<UtilityReadingRecord>, експортує all(),
читає файл назад і порівнює списки через equals:

```text
Записів у сховищі: 6
Заголовок: дата,лічильник,тариф,значення
Фізичних рядків CSV: 7
Відновлених об'єктів: 6
Round-trip: true
Помилок: 1
Рядок 7: Помилка: споживання або тариф має неправильний числовий формат
```

Double.toString відновлюється точно, тому 0.1 + 0.2 і Double.MIN_VALUE
після round-trip побітово рівні. У тесті з полем «Лічильник\nв підвалі» CSV має
7 записів, але 8 фізичних рядків, а відновлений список дорівнює початковому.

## 13. Порівняння реалізацій

Збереження відокремлене від предметної області: Repository, CsvColumn,
DataStorageException, CsvExporter і CsvParser не знають варіанта, а
UtilityReadingRecord відповідає лише за власні поля, інваріанти й розбір.
Експорт і читання мають окремі класи, але спільний заголовок через CsvExporter.header,
тому назви стовпців не дублюються.

Рефлексія повільніша за прямі геттери, а поля шукаються при кожному експорті;
для невеликого навчального набору це не суттєво. Double, читання файла повністю
в пам'ять і один клас запису залишаються навчальними обмеженнями.
Другий формат через Exporter<T> і кешування полів не реалізовувалися: це додаткові завдання.

На запит студента погоджено окремий плоский UtilityReadingRecord замість анотування
поліморфної ієрархії, окремий --export із data/storage.csv і порядок стовпців
за іменами полів. Завдання із зірочкою відкладено. Відхилено трактування
повністю порожнього файла як порожнього набору: порожній набір — файл лише із заголовком.

Старий тест довідки очікує `[--analytics]`, тому новий прапорець додано поруч
замість зміни тесту. Під час підготовки два нові тести мали хибні очікування — порядок
успадкованого поля amount перед code і рядок із п'ятьма полями замість хибного числа;
виправлено очікування, не код.

Під час короткого розбору студент правильно пояснив, що cause потрібен, щоб знати
першопричину, а `? super T` дозволяє передати умову для батьківського типу.
Асистент уточнив, що порядок стовпців задає сортування Java-імен полів, а поле
без @CsvColumn не експортується зовсім, і що експортер знаходить поля рефлексією,
не знаючи класу. Студент спершу вважав причиною хибного числа файлову помилку;
асистент показав ланцюг DataStorageException → DataStorageException →
NumberFormatException. Після прикладу студент правильно визначив, що split(",")
розбиває `Газ,"А, Б, В",5` на п'ять шматків, а CsvParser — на три поля.
Для хибної дати студент назвав верхній рівень помилки; останню причину
DateTimeParseException пояснив асистент. Це фіксує розбір ключових рішень,
а не незалежну перевірку знання кожного рядка. Результати запусків асистента
не приписуються студентові. Джерела: LAB_05.pdf та MAVEN_ACTIONS_GUIDE.pdf.
Студент перевіряє фінальний текст і відповідає за розуміння поданого коду.

## 15. Висновки

Прийняті записи зберігаються в параметризованому сховищі, CSV формується
універсальним рефлексивним експортером на основі @CsvColumn, а помилки
зберігання мають власний тип із причиною. Документний парсер коректно читає
кому, лапки й перенесення рядків; round-trip на контрольному наборі й у тестах
повертає рівні об'єкти. Попередні звіти й тести збережено.

out/readings.csv має стабільну структуру — UTF-8, кома, заголовок, ISO-дати
й числа з крапкою — і стане вхідними даними Python-блоку.
