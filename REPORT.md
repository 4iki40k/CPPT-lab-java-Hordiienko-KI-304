## 4. Контракт даних

Збережено UtilityReading, ElectricityReading, WaterReading, UtilityKind,
CostCalculable та ConsumptionCost. CSV має ті самі чотири поля
`meter;date;value;tariff`, явне UTF-8, без заголовка.

Дата зберігається лише в одному полі LocalDate. Публічні конструктори
продовжують приймати String, getDate() повертає ISO-текст того самого поля,
getLocalDate() повертає календарне значення. DateTimeParseException обгортається
в IllegalArgumentException з причиною; хибний рядок не зупиняє інші.
Парсинг виконується до приватного конструктора, тому CT_CONSTRUCTOR_THROW не повернувся.

Це навмисне посилення валідації: непорожній, але неіснуючий день
2026-02-30 тепер відхиляється в обох режимах. Старий звіт для коректного
контрольного входу й усі старі тести збережено; сумісність із довільними
раніше прийнятними некалендарними рядками не заявляється.

Запити приймають список коректних ненульових об'єктів спільного типу.
Null-список відхиляється через Objects.requireNonNull. Числові обчислення
виконуються в double, тому дробові результати порівнюються з похибкою.

## 5. П'ять Stream-запитів

Усі методи містяться в UtilityQueries й повертають дані, а не друкують звіт.
Для кожного виклику створюється новий stream.

| Метод | Джерело та операції | Результат |
| --- | --- | --- |
| aboveThreshold | List → stream → filter(value > threshold) → toList | List<UtilityReading> |
| consumptions | List → stream → map(getValue) → toList | List<Double> |
| consumptionByMeter | List → stream → collect(groupingBy, summingDouble) | Map<String, Double> |
| consumptionStatistics | List → stream → collect(summarizingDouble) | DoubleSummaryStatistics |
| topByConsumption | List → stream → sorted → limit → toList | List<UtilityReading> |

Поріг контрольного набору — 50. Значення 50 не проходить фільтр,
скінченний від'ємний поріг дозволений, NaN та нескінченність відхиляються.
Map-перетворення зберігає порядок і повторні значення, без distinct.
Результати toList незмінні; це не означає, що всі типи результатів запитів
незмінні: карта та об'єкт статистики є окремими результатами й не змінюють джерело.

## 6. Групування та статистика

Ключ групування — точна назва meter після наявного strip, не UtilityKind.
Регістр і різні назви лічильників не об'єднуються. Значення карти — сума
value, не вартість. TreeMap задає стабільний природний порядок String-ключів,
а summingDouble підсумовує кожну групу. Порожній вхід дає порожню карту.

Статистика містить count, sum, average, min, max. Для порожнього входу
count=0, sum=0, average=0, min=+Infinity, max=-Infinity за контрактом Java.
AnalyticsReport перевіряє кількість і показує для min/max «немає даних».
Нулі в непорожньому наборі відрізняються від відсутності даних.
Locale.ROOT забезпечує крапку й два знаки після неї.

## 7. Компаратор і top-N

Основний ключ — getValue за спаданням; другий — getLocalDate за зростанням.
Reversed викликається до thenComparing, щоб не перевернути порядок дат.
Sorted застосовується до limit; типовий N=5. N=0 повертає порожній список,
від'ємний N відхиляється, завеликий N повертає всі записи.
За рівності обох ключів зберігається початковий порядок ordered stream.
Сортування не змінює вхідну колекцію.

## 8. Optional-пошук

findByMeter виконує filter і findFirst. Крайові пробіли ключа прибираються,
порівняння чутливе до регістру. Null-ключ є помилкою, порожній або відсутній
ключ повертає Optional.empty. За повторного meter повертається перший запис
у початковому порядку, не найновіший і не найбільший.

У форматувальнику Optional.map перетворює знайдений об'єкт на опис,
orElse("Не знайдено") явно обробляє відсутність. Небезпечного get немає.
Контрольні ключі: «Вода» для успіху, «Тепло» для відсутності.

## 9. Еквівалентність і контрольний набір

data/analytics.csv містить шість коректних записів зі споживаннями
100, 60, 60, 50, 30, 10, повторними назвами та датами для другого критерію.
Рядок 7 має неіснуючу дату, рядок 8 — від'ємне споживання.
Старий data/input.csv не змінювався.

| Цикловий еталон | Stream API | Фактичний контрольний результат |
| --- | --- | --- |
| if і додавання прийнятих | filter → toList | Значення 100, 60, 60 для порога 50 |
| Додавання getValue у список | map → toList | 100, 60, 60, 50, 30, 10 |
| Map.merge у циклі | groupingBy + summingDouble | Вода=90, Газ=60, Електроенергія=160 |
| Лічильник, сума, min/max | summarizingDouble | 6; 310; 51.67; 10; 100 |
| Повторний вибір найбільшого | sorted + limit | 100; 60 від 01.09; 60 від 02.09; 50; 30 |
| Пошук із break | filter + findFirst | Вода від 02.09; Тепло відсутнє |

Еталони в тестах незалежні від реалізацій запитів. Для дробових сум
застосовується похибка, а не вимога побітової тотожності різних способів
накопичення double. Джерело та порядок перевіряються до й після запитів.

## 13. Порівняння реалізацій

Запити відокремлені від форматування в AnalyticsReport та від IO/CLI у Main.
ReadingBatch є внутрішнім record результатів перевірки; List.copyOf захищає
склад прийнятої колекції. Спільний processLines не дублює валідацію для режимів.
Проміжні Stream-операції ліниві; кожний незалежний запит створює свій потік.
ToList, collect і findFirst завершують відповідні конвеєри.

Читабельність оцінюється явними етапами й типом результату, а не лише
кількістю рядків. TreeMap забезпечує природний порядок рядків Java, не
спеціальне мовне сортування. Double і читання невеликого CSV повністю в пам'ять
залишаються навчальними обмеженнями. ParallelStream, власний Collector
і дворівневе групування не реалізовувалися: це додаткові завдання.
