## 4. Спільний тип і вибір моделі

`CostCalculable` оголошує `double calculateCost()`.
`UtilityReading implements CostCalculable` зберігає спільні private final поля
meter, date, value, tariff, геттери, фабрику та перевірки.

UtilityReading не зроблено абстрактним: попередній публічний API і тести
використовують `new UtilityReading(...)`. Вимогу спільного контракту виконує
інтерфейс, а звичайний базовий запис залишається сумісним варіантом для газу
та невідомих назв послуг. Final прибрано з класу, але не зі спільних полів.

Обрано спадкування: запис води й електроенергії є різновидами комунального
запису та повторно використовують його стан і перевірки через super(...).
Композиція доречна для відношення «містить», але тут додала б делегування
кожного геттера без потреби. Record ConsumptionCost залишається окремим
значенням-результатом, а не базовим класом ієрархії.

## 5. Підтипи й відмінна поведінка

Ієрархія розміщена в окремих файлах пакета ua.lpnu.kzp:

```text
CostCalculable
    ↑ implements
UtilityReading
    ├── ElectricityReading
    └── WaterReading
```

Обидва підтипи final; додаткові поля private final, сеттерів немає.
Спільні інваріанти перевіряє базовий конструктор, власні — підтип.
Вартість обчислюється й перевіряється при створенні та зберігається в cost;
перевизначений calculateCost повертає відповідний результат.

**ElectricityReading:** нічне споживання nightValue у межах 0..value,
коефіцієнт nightCoefficient у межах 0..1; обидва скінченні.

```text
dayValue = value − nightValue
cost = dayValue × tariff + nightValue × tariff × nightCoefficient
```

**WaterReading:** скінченний невід'ємний wastewaterTariff.

```text
cost = value × tariff + value × wastewaterTariff
```

Це навчальна модель, не твердження про реальні тарифи. Для однакових value=10,
tariff=4 електроенергія з nightValue=4 і коефіцієнтом 0.5 коштує 32,
вода з wastewaterTariff=2 — 60, звичайний запис — 40.

У чотирипольному CSV немає додаткових параметрів, тому фабрика використовує
нічне споживання 0 і тариф водовідведення 0. Додаткові можливості демонструються
явним створенням об'єктів і тестами; старий CSV зберігає value × tariff.

## 6. Enum UtilityKind

Константи: ELECTRICITY, WATER, OTHER. Метод label() повертає український підпис.
fromMeter прибирає крайові пробіли й нормалізує регістр через Locale.ROOT.

| Назви без урахування регістру | Категорія та створений тип |
| --- | --- |
| Електроенергія, електрика | ELECTRICITY, ElectricityReading |
| Вода, гаряча вода, холодна вода | WATER, WaterReading |
| Інші назви, зокрема газ | OTHER, UtilityReading |

getKind() фактичного об'єкта повертає відповідну категорію.
Фабрика використовує звичайний switch за enum тільки для створення об'єкта.
Порожню назву відхиляє спільна валідація до класифікації.

## 7. Equals, hashCode і колекції

Базова рівність враховує фактичний клас через getClass(), meter, date, value
та tariff. Назви порівнюються точно після strip; регістр не ігнорується.
Для double використано Double.compare, для хешу — Objects.hash з тими самими
полями та класом. Числова рівність тут точна, не порівняння з похибкою.

Підтипи спочатку викликають super.equals, потім порівнюють власні параметри:
вода — wastewaterTariff; електроенергія — nightValue і nightCoefficient.
Їхні hashCode включають super.hashCode та ті самі додаткові поля.
Обчислене cost не порівнюється окремо: воно визначається вже врахованими даними.

Перевірено рефлексивність, симетричність, транзитивність, null, чужий тип,
рівні хеш-коди, відмінність підтипів і специфічного стану.
HashSet об'єднує логічні дублікати; HashMap знаходить значення через інший
рівний ключ. У Main залишається List: повторні CSV-рядки не видаляються зі статистики.

## 8. Поліморфізм

Main отримує різнорідні об'єкти через фабрику й зберігає List<UtilityReading>.
Успадкований consumptionCost() викликає calculateCost(), і Java обирає
реалізацію фактичного підтипу. У Main не додано instanceof або switch
для вибору формули. Фабрика вибирає тип, об'єкт визначає вартість,
звіт лише накопичує результати. Форматування звіту залишилося без змін.
