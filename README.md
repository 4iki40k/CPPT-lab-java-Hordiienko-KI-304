## Успадкована модель даних

- `CostCalculable` — спільний інтерфейс із методом `calculateCost()`.
- `UtilityReading` — базовий клас із private final полями meter, date, value, tariff.
  Конструктор перевіряє інваріанти, геттери дозволяють лише читання; сеттерів немає.
  Клас не abstract: старий публічний конструктор збережено для сумісності.
  Перевірка аргументів делегованого конструктора усуває CT_CONSTRUCTOR_THROW
  без вимкнення правила SpotBugs.
  Дата тепер зберігається одним LocalDate: getLocalDate() повертає її,
  getDate() — похідний ISO-текст. Публічний конструктор приймає String як раніше.
- `fromCsv` перевіряє структуру й числовий формат, а потім викликає конструктор.
  Спільний текстовий валідатор зберігає старий порядок повідомлень без дублювання правил.
- `ElectricityReading` і `WaterReading` — final-підтипи з власними незмінними
  параметрами та перевизначеними `calculateCost()` і `getKind()`.
- `UtilityKind` — категорії ELECTRICITY, WATER, OTHER з українськими підписами.
- `ConsumptionCost` — record пари споживання й вартості, з перевіркою компонентів.
  Метод `UtilityReading.consumptionCost()` повертає value та результат
  поліморфного `calculateCost()`.
- `Main` додає до List<UtilityReading> лише прийняті записи після перевірки сум.
  `validateLine` залишено адаптером для попередніх тестів, без власних правил.
- `toString` сутності використовує Locale.ROOT і призначений для людини, не для CSV.
- `equals/hashCode` враховують фактичний клас, спільні поля й власні параметри
  підтипів. Текст порівнюється точно після strip, числа — через Double.compare.
  Обчислене cost окремо не порівнюється. HashSet/HashMap перевіряються тестами;
  Main не видаляє повторні рядки зі статистики.

Чотири поля CSV та стандартний контрольний звіт збережено. Навмисне посилено
перевірку дати: неіснуюча календарна дата тепер відхиляється в обох режимах.

```text
CostCalculable
    ↑ implements
UtilityReading
    ├── ElectricityReading
    └── WaterReading
```

### Вибір підтипу й навчальні формули

Фабрика класифікує назву без урахування регістру та крайових пробілів:

| Назва послуги | Тип |
| --- | --- |
| Електроенергія, електрика | ElectricityReading |
| Вода, гаряча вода, холодна вода | WaterReading |
| Інші назви, зокрема газ | UtilityReading, категорія OTHER |

Електроенергія: `(value − nightValue) × tariff + nightValue × tariff × nightCoefficient`.
Нічна частина в межах 0..value, коефіцієнт у межах 0..1.
Вода: `value × tariff + value × wastewaterTariff`; додатковий тариф невід'ємний.
Це навчальні формули, не твердження про фактичні тарифи постачальників.

Старий CSV містить лише чотири поля: фабрика задає нічне споживання 0
та тариф водовідведення 0, тому зберігається `value × tariff`.
Додаткові параметри доступні через конструктори й демонструються тестами;
п'яте чи шосте поле CSV не приймаються. Switch використовується тільки
у створенні об'єктів, а Main не вибирає формулу за типом.

## Лабораторна №4: запити й аналітика

`UtilityQueries` містить чисті методи без IO та зміни джерела:

| Метод | Результат |
| --- | --- |
| aboveThreshold | Записи з value строго понад скінченний поріг |
| consumptions | Усі value у початковому порядку, включно з повторами |
| consumptionByMeter | Сума value за точною назвою meter, ключі впорядковані через TreeMap |
| consumptionStatistics | Count, sum, average, min, max через DoubleSummaryStatistics |
| topByConsumption | Value спаданням, LocalDate зростанням, потім limit |
| findByMeter | Optional першого запису з точною назвою після strip ключа |

Нульовий N дає порожній список, від'ємний — помилку, завеликий — всі записи.
За рівності обох ключів top-N зберігає початковий порядок. Пошук чутливий
до регістру й не сортує джерело. Null-списки та null-ключ відхиляються.
Скінченний від'ємний поріг дозволений, NaN та нескінченний поріг — ні.
Списки через toList незмінні; карта й статистика є незалежними результатами,
а не твердженням про незмінність усіх повернутих типів.

`AnalyticsReport` форматує результати з Locale.ROOT без прямого виводу.
Порожня карта має вигляд {}, список споживань — [], порожні min/max —
«немає даних», відсутній Optional — «Не знайдено». Count, sum та average
порожньої статистики дорівнюють нулю. У звіті не показуються спеціальні
нескінченності порожньої статистики.

Контрольний поріг — 50, top-N — 5, ключі пошуку — «Вода» та «Тепло».
`data/analytics.csv` містить шість коректних записів і два хибні.
`processLines` спільний для двох режимів: він перевіряє рядки й майбутні суми
до зарахування, повертаючи внутрішній ReadingBatch із захищеним списком.
Цикл прийняття записів збережено для діагностики та переповнення; запити
використовують Stream, а максимум старого звіту тепер отримується зі статистики.

## Предметна задача — варіант 9

Консольна програма для комунальних показників. Вхід — файл UTF-8
без заголовка, один запис на рядок:

```text
meter;date;value;tariff
```

Приклад запису:

```text
Електроенергія;2026-09-01;120.5;4.32
```

Програма перевіряє записи, повідомляє номер і причину пропуску хибного рядка
та обчислює кількість коректних записів, сумарне споживання, загальну вартість
і найбільше споживання. Один текст звіту записується у файл та виводиться в консоль.

Правила:
- Рівно чотири поля; пробіли навколо значень прибираються.
- `meter` і `date` непорожні; дата має бути реальною календарною датою ISO-формату,
  наприклад 2026-09-01. 2026-02-30 і 01.09.2026 відхиляються.
- Числа записуються з крапкою; порожні, нечислові, від'ємні, NaN і нескінченні значення відхиляються.
- Переповнення вартості запису чи накопичуваних сум також спричиняє пропуск рядка.
- Файл не має заголовка, коментарів або CSV-екранування; порожній рядок є хибним записом.
- Без коректних записів суми дорівнюють нулю, максимум — «немає даних».
- Використовується `double`: це навчальні, не банківські розрахунки. Форматування — два знаки після крапки.
- Загальна сума споживання відповідає умові; її не слід трактувати як одну фізичну одиницю для різних послуг.

## Середовище та запуск класу

Потрібен JDK 21. Із кореня репозиторію:

```bash
./mvnw clean compile
java -cp target/classes ua.lpnu.kzp.Main
```

На Windows замість `./mvnw` використовуйте `.\mvnw.cmd`.
Перевірити версії Maven і Java можна через `./mvnw --version`.
Wrapper завантажує Maven під час першого запуску, але не встановлює JDK.

Якщо у Linux використовується старіша Java, у поточному терміналі оберіть JDK 21
(на цій машині він установлений за наведеним шляхом):

```bash
export JAVA_HOME=/usr/lib/jvm/java-21-openjdk
export PATH="$JAVA_HOME/bin:$PATH"
```

Головний клас — `src/main/java/ua/lpnu/kzp/Main.java`.
Навчальний `Hello.java` видалено з поточної версії; його можна знайти в історії Git.
Maven записує результати в `target/`, який не входить до репозиторію.

## Виконуваний JAR

```bash
./mvnw clean verify
java -jar target/lab-java-1.3.0-all.jar
java -jar target/lab-java-1.3.0-all.jar --help
java -jar target/lab-java-1.3.0-all.jar --version
java -jar target/lab-java-1.3.0-all.jar --input data/input.csv --output out/report.txt
java -jar target/lab-java-1.3.0-all.jar --analytics
java -jar target/lab-java-1.3.0-all.jar --analytics --input data/analytics.csv --output out/analytics-report.txt
```

Звичайний запуск читає `data/input.csv` і записує `out/report.txt` відносно
поточного робочого каталогу. З іншого каталогу передавайте явні шляхи.
Шляхи з пробілами беріть у лапки. Каталоги для звіту створюються автоматично;
наявний файл звіту перезаписується. Вхідний і вихідний файли мають бути різними.

`--analytics` за замовчуванням читає `data/analytics.csv` і записує
`out/analytics-report.txt`. Явні шляхи мають пріоритет; порядок прапорця
та --input/--output не впливає на результат. Прапорець не приймає значення
та не може повторюватися. Без нього діє стандартний режим.

Режим `--version` виводить `lab-java 1.3.0`.
Shade Plugin створює окремий `*-all.jar` з головним класом і залежностями
застосунку. JUnit не включається, оскільки має scope `test`.
Версія надходить із `pom.xml` через поле `Implementation-Version` маніфесту.
При запуску класу з `target/classes` замість JAR режим `--version` виводить
`lab-java development`, оскільки метаданих JAR немає.

`--help` і `--version` використовуються окремо й не читають CSV.
`--input` і `--output` можна комбінувати в будь-якому порядку, але не повторювати.
Коди завершення: `0` — звіт сформовано (навіть із хибними рядками),
`1` — помилка читання/запису файла, `2` — неправильні аргументи.

## Тестування та CI

Повна поточна перевірка (компіляція, тести, пакування JAR і SpotBugs):

```bash
./mvnw clean verify
```

SpotBugs аналізує байт-код і зупиняє збірку при виявленні дефектів за поточними
налаштуваннями. Для `java -jar` використовуйте файл із суфіксом `-all.jar`,
а не звичайний JAR без цього суфікса.

Запуск тестів локально:

```bash
./mvnw clean test
```

Навчальний арифметичний тест замінено предметними: `MainTest` перевіряє
валідацію, `ReportTest` — показники, порожні дані, переповнення й локаль,
`CliTest` — аргументи, файлові помилки, UTF-8 і однаковість консолі та файла.
Результати Surefire зберігаються в `target/surefire-reports/`.

Для лабораторної №2 додано `UtilityReadingTest` (47 перевірок),
`ConsumptionCostTest` (11) і `Lab01CompatibilityTest` (1).
Останній порівнює весь текст із контрольним звітом першої роботи,
нормалізуючи лише CRLF/LF. Старі 53 тести збережено; разом — 112.
Лабораторна №3 додає 103 перевірки контракту, enum, підтипів, фабрики,
рівності й хеш-колекцій. Усі попередні 112 тестів збережено; разом — 215.
Лабораторна №4 додає 105 перевірок дат, запитів, форматування, спільної обробки
та CLI. Разом — 320. У тестах є незалежні циклові еталони кожного запиту,
межі порога й N, другий критерій сортування, повтори, порожній пошук та
окрема перевірка незмінності джерела. Запуски з типовими шляхами тестуються
в окремому Java-процесі в тимчасовій теці, не перезаписуючи користувацькі звіти.

Workflow `.github/workflows/ci.yml` запускається після push та при відкритті
або оновленні Pull Request. На кожній із трьох ОС він готує JDK 21 Temurin
і виконує `clean verify` через Wrapper. Залежності Maven кешуються.
CI компілює код, запускає тести, пакує JAR і виконує SpotBugs, після чого
запускає виконуваний JAR у стандартному та аналітичному режимах, звіряє
консоль із файлами й перевіряє, що `--version` відповідає версії POM.
Кожна ОС публікує `*-all.jar` як артефакт із назвою
`jar-<ОС>-<номер запуску>`. На сторінці успішного запуску Actions завантажте
артефакт у секції Artifacts, розпакуйте ZIP і запустіть JAR через Java 21.
Номер запуску CI не є версією програми. Git-тег `v1.0.0` фіксує прийняту
версію лабораторної №1 після merge фінальних правок.
Тег лабораторної №2 — `v1.1.0` — зберігає її прийнятий стан.
Релізний тег лабораторної №3 — `v1.2.0`; старі теги не пересуваються.
Для лабораторної №4 заплановано v1.3.0 після прийняття PR.
Badge вище показує стан стабільної гілки `main`. Стан змін до merge дивіться
в перевірках Pull Request.

Якщо український текст у Windows PowerShell спотворюється, явно виберіть UTF-8
для консолі та потоків Java (так само налаштовано Windows-крок CI):

```powershell
$OutputEncoding = [Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()
java '-Dstdout.encoding=UTF-8' '-Dstderr.encoding=UTF-8' -jar target/lab-java-1.3.0-all.jar --analytics
```
